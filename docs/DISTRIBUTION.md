# 배포와 소스 이력

## 현재 운영 기준

테스트 단계는 **베타 → 정식**으로 운영합니다. 베타는 내부 Windows 10/11 VM 및 부서원 대상 테스트를 포함합니다. 알파·클로즈베타·오픈베타는 앞으로 별도 단계로 구분하지 않습니다.

핵심 QA의 필수 세부 항목 통과 수 ÷ 적용되는 전체 필수 세부 항목 수 × 100으로 평가합니다. Windows 10/11은 각각 집계하며, 유효한 기존 통과 증거는 적용 근거와 원래 해시를 연결해 재사용합니다. 실패·미실행·차단은 통과로 계산하지 않습니다. 사용자 승인 제외 항목은 분모에서 제외합니다.

90% 이상 통과하고 중대 개인정보·인증·데이터 손실 문제, 설치본 서명/무결성·복구와 실제 업데이트 전달 확인을 완료하면 정식으로 전환합니다. 정식 이후에도 문제를 수정해 지속 업데이트합니다.

필수 직원 클라이언트 QA는 CB01 실제 설치/설정 보존, CB02 실제 별도 서버 연결/권한/파일 작업, CB03 변경 영향/중대 문제 검토, CB04 서명/무결성/복구 준비, D01 GitHub/인증 전달, D02 실제 업데이트/연결입니다. 양 OS 총 54개 중 최소 49개 통과가 90% 기준입니다. 장시간 내구, 반복 재부팅/로그인, 전체 장애/화면/DPI 조합, 광범위 백신/은행 호환성 및 지정 PC 파일럿 전체 검사는 확장 QA 이력으로 보존합니다.

2026-11-04 직원 클라이언트 V2.0.5(build37-r1, 파일 버전 2.0.145.0)를 정식 Latest로 전환했습니다. 핵심 필수 세부 검사 54/54개(100%)와 최종 전달 검사를 통과했습니다. GitHub 재다운로드, 두 전용 VM의 실제 구버전→전달된 설치본 업데이트, 별도 SMB 서버 계정·파일 작업, 운영 서버의 허용된 인증 전체 다운로드를 검증했습니다. 영향 없는 기존 설치 UI·전환·권한·복구 결과는 원래 해시와 재사용 근거를 유지합니다.

## 과거 시험 배포 안내

build25/31/32의 당시 예외 배포 및 미완료 QA 기록은 그대로 보존합니다. 예전 알파/클로즈/오픈 명칭을 베타로 정리해도 과거 결과를 Pass로 바꾸거나 기존 2.0 베타를 정식으로 승격하지 않습니다. 태그와 설치파일 바이트, 다운로드 주소는 유지합니다. 기존 채널 키·저장된 선택·접근 권한은 문서 편집으로 변경하지 않습니다.

## Source code 다운로드

GitHub 릴리스 하단의 자동 Source code ZIP/TAR는 해당 태그의 Git 스냅샷입니다. 빌드 25 태그는 `17d1301cdf28beb68d4ac374785d1a25b7a54978`의 1.x 소스 트리를 가리키며, 배포된 2.x MSI의 재현용 소스가 아닙니다. 기존 태그를 이동하거나 검증된 설치파일을 교체하지 않습니다.

이후 패키지는 정확한 소스 커밋에 연결하고 배포 메타데이터에 소스 커밋·설치파일 SHA256·버전/빌드를 기록합니다. 소스가 공개 저장소에 없는 후보를 자동 Source code로 재현 가능하다고 표시하지 않습니다. 비공개 서버 데이터·암호·토큰·개인키·복구본은 소스에 넣지 않습니다.

## 과거 버전

정식 V1.7.5~V1.7.11의 기존 릴리스와 자산을 보존합니다. V2.0.0~V2.0.4, v2.0.0-beta.2~beta.5 및 초기 1.x 태그는 소스 이력이며 현재 배포를 뜻하지 않습니다. 빌드 17 이하 베타 릴리스와 배포 ZIP은 정리되었습니다. 필수 구버전 시험 입력과 QA 기록은 비공개 시험 환경에서 관리합니다.

## 배포 원칙

- 최종 ZIP/MSI는 Releases에서 제공합니다. 기본 브랜치는 소스·문서·공유 빌드 자산을 관리합니다. 기존 공개 파일명/다운로드 URL과 Git 이력을 유지합니다.
- 같은 자산 이름에 다른 바이트를 업로드하지 않습니다. 동일 해시는 다운로드 검증 후 건너뛰고 다른 해시는 실패시킵니다. 수정 패키지는 새 버전/빌드로 게시합니다.
- 빌드 성공은 실제 QA 승인이 아니며, GitHub 게시도 인증된 클라이언트 전달 성공이 아닙니다.
- 새 2.x는 역할/Windows 10·11별 검사표와 정확한 MSI·검사표·정책 해시의 최종 검토를 사용합니다. 베타 품질 확인 → GitHub 게시/재다운로드 해시 확인 → 실제 인증 전달/업데이트 → 핵심 QA 통과율과 필수 배포 확인 후 정식 전환 순서입니다. 상세 기준은 이 문서의 현재 운영 기준을 우선합니다.
- 실제 정책/검사기는 전용 개발 환경의 `next/qa/RELEASE-QA-POLICY.md`, `Assert-ReleaseQA.ps1`을 따릅니다. legacy 1.x Actions를 2.x QA 우회 경로로 사용하지 않습니다.
- 기존 `closed-beta`/`open-beta` 키는 이력과 호환성을 위해 보존합니다. 신규 운영 안내는 “베타”로 통일하며, 앱 화면/채널 전환은 별도 구현과 검증으로 적용합니다.

## Actions 및 검증본 게시

`release-package.yml`은 Windows에서 선택한 legacy 1.x를 빌드하여 Actions 산출물로 보관합니다. push/PR은 릴리스를 게시하지 않습니다. 수동 실행도 `publish=false`가 기본입니다. 게시를 선택할 때는 사전 검증된 ZIP의 정확한 SHA256이 필요하며, 새 빌드가 그 해시와 다르면 중단합니다. ZIP의 시각 정보 등으로 재빌드가 동일하지 않을 수 있으므로 QA 파일과 일치하지 않는 빌드를 대신 배포하지 마세요.

정확한 검증본을 직접 게시하려면 소스가 깨끗한 해당 커밋 체크아웃에서 실행합니다.

```powershell
python tools/release_package.py --version V1.7.12 --package "<검증된 ZIP>" --expected-sha256 "<SHA256>" --source-commit "<40자리 커밋>" --notes-file "<릴리스 안내문>"
```

기본은 검사만 수행합니다. 실제 게시는 `--publish`를 추가합니다. 도구는 1.x만 허용하며 기존 태그 이동·자산 덮어쓰기·Latest 변경·카탈로그 승격을 하지 않습니다. 새 릴리스는 소스 커밋과 해시 메타데이터를 포함합니다. 2.x는 별도 QA 게이트와 게시 경로를 사용해야 합니다.

## 사용 범위

사내 업무용 배포 및 소스 이력 저장소입니다. 개인·외부 기관·기업 대상 업데이트를 제공하지 않습니다. 별도의 프로젝트 오픈소스 라이선스를 새로 부여하지 않았습니다. 폰트 등 제3자 자산의 안내는 해당 자산 폴더에 보존합니다.
